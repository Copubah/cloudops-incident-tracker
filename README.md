# CloudOps Incident Tracker

A lightweight PHP 8.3 and MariaDB incident dashboard. Engineers can create, view, edit, delete, search, and filter incidents. The dashboard shows counts by status and severity plus average time from creation to resolution. The health endpoint checks the database and returns `200` or `503` without connection details.

## Local Docker setup

Requirements: Docker Engine with Compose plugin.

```bash
cp .env.example .env
# Edit .env: set unique DB_PASSWORD and MARIADB_ROOT_PASSWORD values.
docker compose up -d --build
docker compose ps
curl -i http://localhost:8080/health.php
```

Open `http://localhost:8080`. MariaDB data persists in the `mariadb_data` volume. Compose waits for its health check before starting PHP. `database.sql` initializes a new volume only; schema changes to an existing volume require a migration or a deliberate volume reset. `docker compose down` stops the stack. `docker compose down -v` **deletes all incidents**.

The app uses a dedicated MariaDB account generated by the official image. The database port is not published to the host. Credentials come from `.env`, which Git ignores. The web server exposes only `public/`; application configuration stays outside its document root. The UI uses prepared statements, output escaping, input validation and CSRF tokens. This portfolio demo has **no user authentication**. Put an authentication layer in front of it before sharing it with untrusted users.

## Native Kali Linux setup

```bash
sudo apt update
sudo apt install mariadb-server mariadb-client php php-cli php-mysql php-mbstring apache2 libapache2-mod-php
sudo systemctl enable --now mariadb apache2
sudo mariadb < database.sql
sudo mariadb
```

At the MariaDB prompt, replace the example password with a strong unique value:

```sql
CREATE USER 'cloudops_app'@'localhost' IDENTIFIED BY 'YOUR_UNIQUE_PASSWORD';
GRANT SELECT, INSERT, UPDATE, DELETE ON cloudops.* TO 'cloudops_app'@'localhost';
```

Configure Apache `DocumentRoot` to this repository's `public/` directory, and serve `assets/css/style.css` at `/assets/css/style.css` (copy or alias the `assets` directory). Set `DB_HOST=localhost`, `DB_PORT=3306`, `DB_NAME=cloudops`, `DB_USER=cloudops_app`, and `DB_PASSWORD` in Apache's environment, outside the repository. Do not use MariaDB root as the application user. Restart Apache after changing its environment.

## AWS lab architecture

```text
Internet → public Application Load Balancer → EC2 (PHP/Apache + MariaDB containers)
                                               └→ encrypted EBS Docker volume
                 EC2 → Secrets Manager, CloudWatch Logs, Systems Manager
```

Terraform creates a VPC, two public and two private subnets, an internet gateway, an ALB, an EC2 instance, security groups, IAM role, Secrets Manager secret, CloudWatch log group and alarms, and an optional SNS email subscription. The private subnets are reserved for a future managed database; this low cost lab runs MariaDB on the application instance. Only the ALB can reach EC2 port 80. There is no inbound SSH or database rule; use Systems Manager Session Manager for access. The instance has a public IP for package downloads and Systems Manager. The ALB health check calls `/health.php`. Docker writes Apache/PHP and MariaDB logs to CloudWatch; the agent also ships bootstrap and security logs. Alarms watch CPU, EC2 status checks, unhealthy targets, and target HTTP 5xx responses.

**Costs and limits:** ALB hourly use and load balancer capacity, EC2 hours, EBS storage, CloudWatch logs/alarms, Secrets Manager, and possible public IPv4, SNS, and data transfer charges can continue until destroyed. Check current AWS pricing before applying. The lab uses one EC2 instance and colocated database, so an instance failure affects both app and data. HTTP is used to avoid requiring a domain and certificate; traffic is unencrypted. For real use, add ACM HTTPS, authentication, backups, private database hosting, and multi instance availability.

### Deploy only when you choose to

1. Push this repository to a **public** GitHub repository. Set up AWS credentials through your normal AWS CLI profile or SSO; never place them in Terraform files.
2. Copy `terraform/terraform.tfvars.example` to `terraform/terraform.tfvars`, then set `repository_url` to the public HTTPS Git URL. Optionally set `alarm_email` and confirm the SNS subscription email.
3. Run:

```bash
terraform -chdir=terraform init
terraform -chdir=terraform fmt -check
terraform -chdir=terraform validate
terraform -chdir=terraform plan -out=lab.tfplan
terraform -chdir=terraform apply lab.tfplan
terraform -chdir=terraform output application_url
```

The EC2 bootstrap clones the repository, fetches the generated database credentials from Secrets Manager through its instance role, and starts Compose. Allow several minutes for boot and target health. Inspect `/var/log/cloudops-bootstrap.log` through Session Manager if needed. Terraform creates a random database password; **Terraform state contains the secret value**. Use a private S3 backend with bucket versioning, server side encryption, strict IAM access, and a lockfile before collaborating; never commit state or plan files. A separate, precreated state bucket is appropriate because Terraform cannot reliably create its own backend during `init`.

To end charges, run `terraform -chdir=terraform destroy` with the same AWS profile and variables. Secrets Manager has a seven day recovery window, so verify any remaining billable resources in the AWS console. Export incident data before destroying the instance or volume.

## CI and checks

GitHub Actions lints PHP, builds the Docker image, and checks Terraform formatting and validity. It has **no deployment credentials and no deploy step**. Run the checks locally with `find config public -name '*.php' -print0 | xargs -0 -n1 php -l`, `docker compose --env-file .env.example config --quiet`, and `terraform -chdir=terraform fmt -check`. Terraform `init` and `validate` need network access to download providers.
